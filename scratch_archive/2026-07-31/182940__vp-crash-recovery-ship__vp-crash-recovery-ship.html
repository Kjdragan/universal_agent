1 · STEP 0 evidence — verified, with two corrections

Seven vp.coder.primary missions between 2026-07-08 and 2026-07-15 carry the exact crash signature (message="Unknown error", empty final_text, trace_id=null) in vp_state.db. The proven in-gap instance: vp-mission-d51ed9c8… wrote its apply-script, ran it ("ALL EDITS APPLIED"), validated (ruff-exit=0 plus a regression test), staged the work with git add — and was killed 0.25 seconds after staging. The identical fix was then redone by hand 17 minutes later (commit ef424272, #1417). That redo cost is exactly what this build eliminates.

Two corrections to the inherited premise, folded into the design:

Inherited beliefWhat prod actually showed
Opaque CLI-session death in claude_cli_clientThe July cluster rode the in-process SDK lane (claude_code_client → ProcessTurnAdapter); "Unknown error" is what an absolute-backstop kill collapses into
Actively bleeding failure classDormant since 2026-07-15 — the 1800s backstop pin was fixed; the collapse path still exists at 7200s, so the machinery is insurance plus a landed dependency, not a live fire

Main was literally waiting for this module: #1328 (merged the same day) lazy-imports vp.apply_checkpoint.has_validated_apply and silently degraded to heuristics until this PR landed.

3 · The observability gate, passed on merit

The gate that killed the prior attempt (test_subprocess_spawns_use_observability_protocol) passes with no allowlist entry: the runner classifies every pipeline child's termination with classify_worker_exit — nonzero, signaled (negative rc, e.g. OOM-kill), timeout-killed (per-step backstop, rc 124) — echoes it to stderr (landing in the turn's run.log) and records it durably in the checkpoint's extra["worker_exit_by_step"].

Deliberate non-wiring: the runner does NOT open or close task-hub run rows. It is a nested child inside a turn the parent CLI client already tracks end-to-end; a child calling _close_run would steal the parent's close mid-turn and double-book the ledger. This "nested-child spawn pattern" is now documented in the Task Hub doc.
