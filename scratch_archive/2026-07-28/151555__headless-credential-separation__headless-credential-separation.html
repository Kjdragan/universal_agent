Separate the headless Claude credential from the interactive one

Proposal for later evaluation · written 2026-07-28 · not scheduled, not started

The problem in one line: a credential that headless agents legitimately need lives in Infisical under the exact name Claude Code auto-detects for interactive auth — so every code path that bulk-injects secrets silently hijacks interactive sessions.

The proposal: rename the vault entry to a name Claude Code does not auto-detect, and have the one consumer read it explicitly. This converts a recurring class of bug into a structural impossibility.

Status: the symptom is already fixed three different ways and nothing is broken today. This is about removing the cause. It touches a production auth path, so it wants its own session.

1. What actually happened, and why it happened three times

CLAUDE_CODE_OAUTH_TOKEN is produced by claude setup-token. It is a programmatic credential, meant for headless use. Claude Code auto-detects it from the environment and, when present, it overrides the stored subscription login at runtime. The /login screen states this outright:

CLAUDE_CODE_OAUTH_TOKEN is set in your environment and will override
this login token at runtime.

The consequence is not an error. It is a silent downgrade. The session presents as Claude API instead of Claude Max; on API auth, Fable 5 is billed to separately-purchased usage credits rather than the plan; /model fable is refused, or the session quietly falls back:

Switched to Sonnet 5 for this session · Fable 5 requires usage credits · /model to change

Inference keeps working, so nothing looks broken. The tell is that plan usage sits nearly untouched (wk 10%) while the model behaves as though limits were exhausted. That mismatch is what took a while to spot — the symptom impersonates a quota problem.

The structural cause

The token is stored in Infisical, and initialize_runtime_secrets() injects the full secret set with overwrite=True. So any entry point that bootstraps Infisical inherits it. It reached interactive sessions through three independent doors, each of which had to be fixed separately on 2026-07-28:

#DoorHow it arrivedFix
1claude2() in ~/.bashrcExplicit shell export from ~/.secrets/claude_acct2.token, dating from when acct2 had no credentials of its ownRemoved; acct2 now uses its own .credentials.json
2_claude_launcher.py (the claudereal path)Infisical bootstrap, overwrite=True — a shell unset cannot help, the value arrives inside the launcherAdded to _INTERACTIVE_STRIP_NAMES (PR #1533, merged + deployed)
3claudezai (the -glm lanes)infisical run --env=development injects the whole dev setunset in the launcher

Three doors, one cause. Each fix was correct and each was reactive. Nothing prevents a fourth door — any new script, service, or lane that bootstraps Infisical inherits the same problem, and the failure is silent.

2. Why the obvious fix — delete it — is wrong

Deleting the secret would break Cody's anthropic lane, silently

My first instinct was that the token might be vestigial now that both accounts authenticate from their own .credentials.json. The code says otherwise. On origin/main:

src/universal_agent/vp/clients/claude_cli_client.py::_build_cli_env
  → forwards CLAUDE_CODE_OAUTH_TOKEN into the `claude --print` subprocess
    for every Cody mission running in anthropic mode

tests/unit/test_vp_failure_rescue.py
  → 9 assertions pinning that forwarding behavior

The comments there show it was added deliberately to fix the opposite bug: an earlier version didn't forward it, and headless missions failed to authenticate.

The reason is structural. A spawned headless claude --print subprocess has no interactive login to fall back on and cannot perform an OAuth flow. It needs a token handed to it — which is exactly what setup-token exists to produce.

So the credential is correct for headless spawns and wrong for interactive sessions. Deleting it would fix today's symptom by breaking the VPS's entire Cody anthropic lane, and the failure would surface only the next time a mission ran.

3. The proposal

Keep the credential. Change its name so that the name Claude Code auto-detects simply does not exist in the vault.

StepChange
1Add a new Infisical secret, e.g. CLAUDE_CODE_OAUTH_TOKEN_HEADLESS, with the same value as the current bare entry.
2Teach the one consumer to read the new name, falling back to the old one during rollout:
os.environ.get("CLAUDE_CODE_OAUTH_TOKEN_HEADLESS") or os.environ.get("CLAUDE_CODE_OAUTH_TOKEN")
in claude_cli_client.py::_build_cli_env. It already sets env["CLAUDE_CODE_OAUTH_TOKEN"] on the child, which is correct and unchanged — the child should receive the auto-detected name.
3Update the tests to cover both names (the existing suite already has a "both names during rollout" case, so the pattern is established).
4Ship, deploy, and verify with a live Cody anthropic mission.
5Only then delete the bare CLAUDE_CODE_OAUTH_TOKEN from Infisical, and remove the fallback in step 2.

The interactive strips added on 2026-07-28 stay regardless. They become belt-and-braces rather than the only defense — which is the right relationship for a security-adjacent guard.

4. What it achieves — and what it doesn't

Achieves

  • Turns a recurring bug class into a structural impossibility. No future script, service, or lane can accidentally inherit interactive auth, because the auto-detected name is not in the vault to inherit. This is the whole point.
  • Removes a silent-failure mode. The current bug produces a working session with a downgraded model and no error. That is the worst shape a bug can take — it took screenshots and a header inspection to catch.
  • Makes intent explicit at the vault layer. A reader seeing …_HEADLESS knows what it is for. The bare name reads as "the" Claude token, which is precisely the misreading that produced three doors.
  • Reduces credential blast radius. An Anthropic subscription credential currently lands in every Infisical-bootstrapped process, including -glm sessions that talk to a third-party provider. Naming it out of auto-detection narrows that to the one consumer that asks for it by name.

Does not achieve

  • It does not reduce token cost or change any model routing. This is a correctness and hygiene change, not a performance one.
  • It does not fix anything currently broken. All four lanes work today. This prevents recurrence; it does not repair.
  • It does not stop the bare name leaking from a shell. If something exports it by hand, Claude Code still auto-detects it. The interactive strips cover that, which is why they stay.
  • It does not address the suffixed variants. …_CLAUDEREAL / …_CLAUDE2 / …_ACCT2 are separate secrets used by lab_common/inference.py via LAB_MAX_ACCOUNT for max-mode subagents. They never collided because they don't match the auto-detected name — which is, in miniature, the proof that this proposal works.

5. Risk, blast radius, and how it fails

RiskSeverityMitigation
Cody anthropic missions lose auth on the VPSHigh — this is the real oneThe rollout order is designed around it: add the new secret, ship a consumer that reads new-or-old, verify a live mission, and only delete the old name afterward. At no point is there a window where neither name resolves.
An unknown consumer reads the bare nameMediumA repo-wide grep found only claude_cli_client.py plus tests and demo scratch copies. Re-run the grep at implementation time — the estate moves.
Rollout stalls half-done, leaving two secrets foreverLowHarmless (they hold the same value) but it forfeits the benefit — the bare name still exists to be inherited. Step 5 is the step that actually delivers the fix; a half-rollout achieves nothing.
Failure is silent, as beforeMediumVerification must be a live Cody mission, not a unit test. Unit tests pass on both names by construction; only a real spawn proves the VPS path.

Reversibility: high at every step until step 5, and even then recoverable by re-adding the secret. No data is destroyed; the value is unchanged throughout.

6. Verification plan

  1. Re-run the consumer grep across ~/lrepos, excluding worktrees and vendored copies. Confirm _build_cli_env is still the only real consumer.
  2. Add the new secret; confirm both names resolve from a VPS shell.
  3. Ship the consumer change; confirm PR-Validate green and deploy green.
  4. Run a live Cody mission in anthropic mode and confirm from the run log that the subprocess authenticated. This is the gate — everything before it is circumstantial.
  5. Delete the bare secret. Re-run the live mission. Then open a fresh claudereal-max and confirm the header still reads Claude Max.
  6. Remove the rollout fallback in a follow-up PR.

7. Alternatives considered

OptionVerdict
Do nothing — the three strips already workDefensible. Nothing is broken. The cost is that every future Infisical-bootstrapping entry point is a latent fourth door, and the failure is silent. Reasonable if the estate stops growing new lanes; less so if it doesn't.
Delete the secret outrightRejected — breaks Cody's anthropic lane (§2).
Move it out of Infisical to a file the headless path reads directlyViable, and arguably cleaner still — it leaves the vault entirely. But it needs a secure-distribution story to the VPS that Infisical already solves, so it trades one problem for another.
Exclude it at the initialize_runtime_secrets() layer for interactive callers onlyThis is effectively what fix #2 does. It works, but it is a per-caller opt-out — the same shape as the current situation, requiring every future caller to remember.

8. What I'd want from you to proceed

Two decisions, both yours:

  1. Is preventing recurrence worth touching a production auth path? The honest answer is that the current state is safe and this is insurance. If Cody's anthropic lane is load-bearing right now, "do nothing" is a legitimate choice.
  2. Do you want the rename, or the cleaner move out of Infisical entirely? The rename is smaller and lower-risk; the move is more thorough but needs a distribution mechanism.

Nothing here is started. The 2026-07-28 fixes (three interactive strips, PR #1533 merged and deployed) stand on their own and are not blocked by this proposal.
