universal-agent-proactive-demo-nuggets — what is actually wrong

Investigated 2026-08-01, updated 2026-08-02 (fidelity gate root-caused and fix verified) · evidence from journald, systemd cgroup accounting, the live activity-state DB, demo_factory build stats, and the deployed source

Bottom line

The 2026-08-01 run did not fail. Its main python exited cleanly with status 0 at 06:36:47 after completing every phase including the zero-backlog swipe. The result=timeout systemd recorded was a post-exit cgroup cleanup failure — leftover claude children that ignored SIGTERM.

There is a real one-line subprocess bug — the per-build timeout kills only the direct uv child and orphans the claude grandchildren, which stay charged to the service's cgroup. Proven, and worth fixing on its own terms. fixed & deployed But it is not what caused the OOMs — see below.

The OOMs have a different cause, and it is the interesting one. All three (07-20, 07-22, 07-27) fire shortly after the demo under test downloads a multi-gigabyte ML model — 954 M, 2.9 G, 1.7 G. On 07-22 the weights finished landing at 05:37:20 and the cgroup died at 05:38:49, 89 seconds later. This job builds demos like "Run Alibaba OvisOCR2 Locally" and then executes them, loading the weights with CPU torch inside a 1 GB-capped cgroup on a GPU-less 4-core box. structural — needs your call

Your instinct on MemoryHigh=2G was right, and my first read was wrong. The reassuring "peak was only 1.0G" is a clamp reading — pinned at MemoryMax=1G with 1.16G spilled to swap — and #1579 was not even live that night (it landed 13h later). Real demand was ~6 GiB. MemoryHigh=2G binds on every observed night. removed

And the fidelity gate — the thing that looked most broken — was right all along. It stopped passing builds on 2026-07-31, not 07-18 (that earlier figure came from an incomplete ledger; see §3). The cause was a build-model swap nobody decided: a dead config went live on a manual demo_factory pull at 02:06 UTC and the very next run built with claude-sonnet-5 instead of claude-opus-4-8. Sonnet self-certifies — it declares the goal met without running the verifier — so the artifact runs but implements nothing, and the judge correctly scores it 0/N. root-caused & fixed

And proven. A controlled verification build on claude-opus-5 + xhigh, run 08-02 07:19 on the same capability that Sonnet had timed out on, came back PASS — gating 4/4, votes 2/2, holistic delivers, rc=0, in 33 minutes for $4.69, ending by echoing the real verifier token. §3 has the three-model comparison.

2. The orphaned process group — a real bug, but not the OOM cause

The deployed services/proactive_demo_nuggets.py::_default_build_runner is:

def _default_build_runner(argv: list[str]) -> subprocess.CompletedProcess:
    """Run build_demo.py as a subprocess (the injection seam tests replace)."""
    return subprocess.run(
        argv,
        capture_output=True,
        text=True,
        timeout=_build_timeout_seconds(),
    )

Verified live on the VPS: grep -c "killpg\|start_new_session" on /opt/universal_agent/src/.../proactive_demo_nuggets.py returns 0.

On TimeoutExpired, CPython kills only the direct child — here uv. The process tree below it survives:

systemd oneshot cgroup
└─ python -m ...proactive_demo_nuggets_cron        [the main process]
   └─ uv run --project demo_factory python build_demo.py     ← only THIS gets killed
      └─ python build_demo.py
         └─ claude --print --output-format stream-json ... /goal ...   ← ORPHANED
            └─ notebooklm-mcp                                          ← ORPHANED

Orphans re-parent to PID 1 but cgroup membership is inherited at fork and does not change on re-parenting. The orphaned claude tree therefore stays inside system.slice/universal-agent-proactive-demo-nuggets.service, keeps counting against MemoryMax, and outlives the main process.

Reproducible proof

Mirroring _default_build_runner exactly, with a sh → python → sleep tree:

CaseImplementationSurviving grandchildren after timeout
A — current codesubprocess.run(argv, capture_output=True, timeout=N)1 orphaned
B — the fixPopen(..., start_new_session=True) + os.killpg(SIGKILL)0

This is now a committed regression test (test_build_runner_timeout_reaps_the_whole_process_group), run as a negative control against the old runner: it fails with “1 orphaned grandchild process(es) survived the build timeout” and passes with the fix.

The build loop then continues to the next candidate after a timeout — so orphans accumulate within a single run, and each subsequent build has less headroom than the last.

3. The fidelity gate — not broken, and here is what actually broke

Correction to an earlier version of this exhibit. It said the gate had rejected everything since 2026-07-18. That was wrong, and the error is instructive: it came from reading demo_factory/lessons/build_stats.jsonl, which is an incomplete ledger — 21 rows, newest pass 07-18. The authoritative record is each workspace's eval_report.json, and those show passes on 07-21, 07-22, 07-23, 07-26, 07-28, 07-29 and 07-30. The real collapse starts 07-31, and that one-day precision is what made the cause findable.

rc=3 does not mean the demo is broken. In demo_factory/scripts/build_demo.py::Driver.finish, rc=3 means land != "PASS", and land_demo.py computes final_pass = passed and eval_passed — the deterministic verifier and a Gemini fidelity judge voting by strict majority.

What changed on 07-31: a build-model swap nobody decided

demo_factory/scripts/model_tiers.py right-sizes the generic class to sonnet, and this lane passes no --build-model. That config was dead until the VPS demo_factory checkout was pulled to 71e2868 at 2026-07-31 02:06 UTC (from its git reflog). The very next nuggets run — 2h46m later — built with sonnet:

Not a budget cap, not a bad model id, not a thinking deficit. Every session ended stop_reason=end_turn at 49–58 turns; the transcripts record the correct model: claude-sonnet-5; and sonnet emitted more thinking events (286–717) than opus (252–363). The session result text is the tell:

Effort is a one-step raise — per the official docs the default is high, not medium.

The structural weakness underneath — still open

The sharpest way to put it: the stronger model was masking a weak gate. goal_condition.py hard-requires the literal DEMO_VERIFY: PASS demo_id=<id> token, which is right — but that token only proves the README ## Run command executed, not that the capability exists. A demo can print it while implementing nothing. The pipeline has always accepted "the model says it's done"; Opus is conscientious enough that this never showed. Reverting the model restores output, but if Opus drifts or another right-sizing lands, it recurs. That gap is unfixed — the nightly report is a detector, not a fix.

A bonus finding: the box's "load 15" is a phantom, and it is the desktop SSHFS bridge

Chasing whether contention explained the slow runs turned up something unrelated but worth knowing. During this investigation the VPS showed load average 15.2–15.6 pinned for 100 minutes — while sar reported the CPU 85–94 % idle, %iowait < 1.1, procs_blocked = 0, and sda %util 0.1–4.7 %.

The cause is /home/kjdragan, the SSHFS mount back to the desktop:

kernel: INFO: task systemd-fstab-g:247133 blocked for more than 614 seconds.
        stack: fuse_getattr / fuse_do_getattr / fuse_simple_request / fuse_update_get_attr

Every systemctl daemon-reload forks systemd-fstab-generator, which stat()s /home/kjdragan; against a degraded FUSE mount that call blocks uninterruptibly and forever. There were 218 daemon-reloads on 08-01 alone. FUSE waits count toward load average but never reach procs_blocked — hence phantom load. Load collapsed from 15.3 to 0.99 within three minutes of the mount deactivating at 00:57:20.

Two practical consequences: (1) the io full avg60 = 7.11 pressure reading is the same artifact, not real disk contention; (2) this is why systemctl calls against this box kept returning "Connection timed out" throughout the investigation. As of 02:12 UTC 08-02 the bridge was down — no sshfs mounted, home-kjdragan.automount in inactive / Result=resources.

Closed out — root-caused and fixed in a parallel session (PR #1591, deployed 15da9ac7 at 03:14 UTC). That session went further than this one and corrected the mechanism I inferred: systemd-fstab-generator runs on every daemon-reload and statx()s each fstab mount point; against a wedged FUSE mount that call blocks uninterruptibly and systemd kills the generator sandbox at its hard 90 s timeout. At roughly 63 reloads per deploy that is ~95 minutes inside a timeout 30m — the recurring exit-124 deploy failures. Also worth knowing: "Failed to fork off sandboxing environment" is a misnomer — the fork succeeded; safe_fork(FORK_WAIT) maps a non-zero child exit to -EPROTO.

Fix: the bridge moved out of /etc/fstab into native home-kjdragan.mount/.automount units, plus a watchdog timer. Measured on the same wedged mount: 90.42 s → 0.41 s. Re-verified live at 03:29 UTC: reload 0.42 s, zero fuse.sshfs lines in /etc/fstab, bridge active/active. The phantom load and the systemctl timeouts described above are gone.

6. Verdicts on Q1–Q5

Q1 — Was the memory ceiling the real constraint, or a symptom? BOTH — and my first answer was wrong

I initially called it a pure symptom, reasoning that "peak was 1.0 GiB, so 1G was nearly enough." That reasoning is invalid — and the arithmetic proves it cleanly. MemoryPeak = 1075073024 is 1 331 200 bytes above exactly 1 GiB — 325 pages. The per-CPU charge stock on this box is nr_cpus × MEMCG_CHARGE_BATCH = 4 × 64 pages = 1.0 MiB. That overshoot is the charge-batch slop over a hard memory.max of 1 GiB. A free-running peak does not land 0.12 % above a round power of two.

The four-night series settles it beyond argument — resident peak identical to the decimal while swap varies 10×:

NightCPU consumedMemory peakSwap peak
2026-07-1510m26s1.0G380.7M
2026-07-212h51m08s1.0G1.9G
2026-07-231h01m44s1.0G189.4M
2026-08-0122m59.6s1.0G1.1G

That is a ceiling being read as headroom. You cannot measure demand off a limit the job is sitting on.

The kernel's memcg records give the real number. Three CONSTRAINT_MEMCG oom-kills of this unit (not one), all at limit=1048576kB:

2026-07-205.08 GiB~1.0 GiB~6.05 GiB100 % direct (pgscan_kswapd = 0)

So the ceiling was a real, binding constraint — the 07-27 OOM stack is literally do_swap_page → swapin_readahead → … → mem_cgroup_out_of_memory: it died while paging back in.

And here I have to correct myself again — this time on the root cause of the OOMs. I attributed the 6 GiB to orphan accumulation. The adversarial pass found that 2 of the 3 OOM nights had no orphan at all, and 2 of the orphan nights had no OOM. The variable that tracks all three is something else entirely, and the timestamps are unambiguous:

This job builds demos that download multi-gigabyte ML models and load them with CPU torch — inside a 1 GB-capped cgroup, on a GPU-less 4-core box. The 07-27 demo is literally titled "Run Alibaba OvisOCR2 Locally". Its workspace is 1.1 GB of .venv alone; the shared HF cache is now 8.9 GB. The verifier executes the demo's own ## Run command, which is what pulls the weights into anon memory. That is where 6 GiB comes from — not from orphans.

Per-phase: judge ≈ 23 s, negligible memory. Each build ~600 MB of tooling (claude 457 MB + notebooklm-mcp 98 MB + uv 47 MB) for 22–60 min — plus whatever the demo under test allocates, which for a model-loading demo is multiple GB and dwarfs everything else. Swipe < 1 min, negligible.

Q2 — Is MemoryHigh=2G a mistake? YES — you were right, I was wrong now removed

My first pass called it inert because peak was below 2 G. That rested on the same invalid clamp reading, and on a second error: #1579 was not live during the 08-01 run at all. It landed at 19:27 UTC on 08-01; the run was 04:50→06:39. Independent proof from the run itself — its stop-sigterm expired at exactly 90 s after main exit (06:36:47 → 06:38:17), which is DefaultTimeoutStopSec, not the TimeoutStopSec=300 that #1579 added. There has never been a run under these limits.

Corrected verdict: every observed night exceeded 2 GiB of anon demand — 6.05, 5.92, 6.58 on the OOM nights and 2.16 on the lightest surviving one. MemoryHigh=2G therefore binds every time. And the mechanism you worried about is exactly right: memory.high does not kill, it forces direct reclaim and imposes an explicit sleep penalty on return to userspace (mem_cgroup_handle_over_high). It trades a loud result=oom-kill for a quiet result=timeout — the precise diagnostic confusion that cost a day here.

There is also nothing to protect: box-wide /proc/pressure/memory reads 0.00 / 0.00 / 0.00 with ~11.7 GiB available on a 16 GiB host, and the job is already bounded end-to-end by wall clock. So memory.high here is pure downside. Removed in PR #1588.

On the decisive evidence you asked for: you were right that memory.events's high counter and memory.pressure settle it — and they were genuinely unreadable, because a Type=oneshot destroys its cgroup on exit. That gap is now closed: PR #1588 adds an ExecStopPost= post-mortem that runs inside the cgroup while it still exists (verified empirically, and it fires on abnormal exits too). From tonight, every run records its own high/max/oom counters and pressure totals.

Q3 — Why is runtime growing run over run? IT ISN'T GROWING — it tracks build count, exactly

The series is not monotonic: 45m → 64m → 102m → 24m → 94m → 138m → 106m. It is bimodal, and the variable is simply how many demos got built:

  • 1-build nights (07-26, 07-29): 45m and 24m.
  • 3-build nights (07-28, 07-30, 07-31, 08-01): 102m, 94m, 138m, 106m.
  • Builds run strictly sequentially, and Σ(build durations) accounts for the wall clock to within seconds — on 08-01, 105m47s of builds inside a 105m56s run (99.86 %).

So: not a growing pool (Q4 refutes that), not retries (there are none in the pipeline), and not cross-lane contention — proactive-demo-build-sweep fires at 13:30/18:30/23:30 UTC and is an enqueuer, not a build lane; it never overlaps 04:51. Heavy neighbours were present on 07-28 and 07-31 but absent on 07-30 and minimal on 08-01 — two of the other slow runs — so contention does not explain the split. Build count does, on every single night.

The 3 × 3600 + slack assumption holds. Worst observed is 07-31 at 137m23s of build time; even three fully-timed-out builds would be 10800 s plus a ~23 s judge and a <60 s swipe, inside the 12000 s budget. TimeoutStartSec is not the binding constraint and #1419 was sound.

Q4 — Does swipe-runs-last hurt us? REAL BUT SELF-HEALING — the feedback loop is REFUTED

The mechanism is real and confirmed in code: proactive_demo_nuggets_cron.py::main calls run_zero_backlog_swipe on the line after select_and_build_nuggets, and it is not in a try/finally — a hard kill skips it. 2026-07-27 proves it: that OOM-killed run swept 0 rows.

But the runaway loop you feared does not exist in the data. Measured read-only against /opt/universal_agent/AGENT_RUN_WORKSPACES/activity_state.db:

  • Current open un-built pool: 14 rows (vs 767 cancelled).
  • Inflow is flat: 8, 8, 17, 19, 18, 15, 19, 6, 11, 17, 12, 18, 15, 10, 10 per day (07-18 → 08-01).
  • 07-27 swept 0 — and 07-28 swept 31, roughly two days' inflow. The next night's swipe catches up automatically, because the filter is "everything still open", not "today's rows".
  • Still-open rows by creation day: 06-23 × 1, 07-31 × 3, 08-01 × 10 — i.e. essentially just today's inflow awaiting tonight's run.

So: worth hardening (cheap), but it is not a cost driver and it is not compounding.

A different recycling loop does exist, though, and it is the one worth your attention. The 08-01 swipe reported swept: 11, kept: 0, preserved_approved: 1 — and three of those cancelled rows were re-opened at 13:35:05 the next day by the following day's ingest. Two of the three are the failed builds themselves. The cause is in sweep_unbuilt_pending_builds: it preserves only built_summary["built"], which was empty (kept: 0) because every build ended rc=3. So a build that ran for 40 minutes, produced a working demo, and was rejected by the fidelity judge is swept as "un-built" and re-ingested to be built again tomorrow.

Combined with §3 — where the fidelity gate rejects everything — that is a genuine loop: the same candidates can be rebuilt night after night, each attempt costing 20–60 minutes of inference, each rejected, each re-queued. It has not blown up the pool size (the numbers above show it hasn't), but it is burning real money. It disappears the moment the fidelity gate is fixed.

Q5 — One systemd start, or per-build units / a bounded queue? KEEP ONE UNIT

Keep the single oneshot. The work is genuinely sequential and bounded (≤3 builds, hard-capped at 3600 s each), the total fits comfortably in the existing budget, and the current shape keeps the judge → build → swipe invariant in one place where the daily-ceiling accounting is already correct. Per-build units would buy per-build memory isolation and independent failure — but at the cost of splitting the 5/day ceiling logic across unit boundaries, needing a queue/state machine to sequence them, and making "did the swipe run?" a distributed question. That is a lot of machinery to solve a problem that a 20-line process-group fix already solves.

The one structural change worth making is smaller: move the swipe so it always runs (see recommendation 3).

7. Was PR #1579 right?

It was built on a premise that does not hold, and it is incomplete. One part of it is genuinely good.

  • TimeoutStopSec=300 — genuinely useful, keep it. This is the one change that addressed the real 08-01 failure mode. It gives systemd longer to reap leftovers instead of giving up after the 90 s default.
  • MemoryHigh=2G — a mistake, exactly as you suspected. It binds on every observed night (lightest demand 2.16 GiB), throttles rather than kills, and converts a loud OOM into a quiet timeout. removed in #1588
  • MemoryMax=3G — under-sized against observed demand, but defensible now. Measured demand on the OOM nights was ~6 GiB, so 3G would not have saved them. Post-#1587, with orphan trees reaped, expected demand is the ~2.16 GiB baseline and 3G is reasonable as fault isolation. It is now documented as a deliberate choice rather than a fitted limit, to be raised to 6G only if the new post-mortem shows a post-fix run exceeding it.

Two factual corrections to the diagnosis written into the unit's comment:

  1. "the judge + its claude CLI children peaked at exactly 1.0G … and died at the former MemoryMax=1G ceiling" — on 08-01 the process exited 0. It did not die. The 1.0 G figure is the cgroup pinned at its old limit with 1.16 G of overflow in swap.
  2. None of #1579's limits were in effect when those numbers were taken. It landed ~13 h after the run it cites. Tonight (2026-08-02 04:51 UTC) is the first run under any of it — and now also the first under #1587 and #1588.

8. Ranked recommendations

1. Kill the build's whole process group on timeout  SHIPPED & MERGED

PR #1587 — Popen(..., start_new_session=True) plus SIGTERM→SIGKILL killpg escalation on timeout and on any abnormal exit, with the CompletedProcess contract preserved. Merged with all checks green; deploy ran on merge. risk: low — confined to one function that already had a test-injection seam; 23/23 unit tests pass, ruff clean, doc_audit.py 0 errors, and the canonical ADR was updated in the same PR.

The regression test was validated as a negative control: reverted against the old runner it fails with "1 orphaned grandchild process(es) survived the build timeout"; with the fix it passes. A test that cannot fail proves nothing, so this was checked explicitly.

2. Investigate the fidelity gate — it is rejecting 100% of builds HIGHEST VALUE

Seven consecutive builds have passed the deterministic verifier and been rejected by the Gemini judge; the last pass was 2026-07-18. This is the difference between a job that costs 1–2 h/night and produces demos, and one that costs the same and produces nothing. Two concrete leads: the voter panel shrank from 5 to 2–3 (strict majority over 3 is much harsher than 4/5), and herdr failed at 1/3 despite a holistic verdict of "delivers". design decision — your call: is the gate correctly catching a real regression in build quality, or has the gate itself regressed? I did not change it.

ANSWERED 2026-08-02 — the gate was correct; the builds regressed. Cause was the claude-opus-4-8 → claude-sonnet-5 swap on 07-31 (§3), fixed in PR #1596 by pinning claude-opus-5 + xhigh effort on the unit. Both leads above turned out to be red herrings: the panel shrinking 5→3 came from the same commit but shifts the strict-majority threshold by <4pp, and herdr's 1/3-with-"delivers" is just what a near-miss looks like. The per-sample pass rate itself collapsed (~0.7 → ~0.12). Leaving the original text above rather than rewriting it, so the reasoning trail stays honest.

3. Make the zero-backlog swipe unconditional

Wrap the select_and_build_nuggets call in try/finally so an exception cannot skip the swipe, and/or add ExecStopPost= running the swipe standalone so even a killed run resets the pool. risk: low, value: low — the DB shows the current behaviour self-heals, so this is hygiene, not a fix. Not shipped; say the word.

3b. Remove MemoryHigh, and capture the cgroup evidence  SHIPPED

PR #1588 — drops MemoryHigh=2G, records why MemoryMax=3G is now a deliberate fault-isolation choice rather than a fitted limit, and adds ExecStopPost= → scripts/nuggets_cgroup_postmortem.sh. The post-mortem runs inside the unit's cgroup while it still exists — verified empirically against a live cgroup on the box — and fires on abnormal exits too, so oom-kill and timeout runs are captured. From tonight, journalctl -u … | grep CGPM gives you memory.events (high/max/oom), memory.pressure, swap peaks, and any leftover pids still charged at teardown. That closes the "unmeasurable" gap permanently. It also corrects the unit's false "Opus /goal" and --video comments. risk: low — the post-mortem is prefixed - so it can never change the unit's result.

2b. Decide what happens when a demo wants to run a 3 GB model on a GPU-less box STRUCTURAL

This is the memory question that actually matters, and it is a design decision, not a limit. The factory keeps selecting "run <model> locally" tutorials, then executing them on a 4-core VPS with no GPU — pulling 954 M / 1.7 G / 2.9 G of weights into a capped cgroup. All three OOMs are this. The shared HF cache is already 8.9 GB. Options, roughly in order of how much they change:

  • Filter at the judge. Teach the golden-nuggets judge to reject candidates whose demo would require local model inference — it already scores for "specific technical capability"; add "runnable on a GPU-less 4-core box" as a hard gate. Cheapest, and it also stops burning an hour on demos likely to fail the fidelity judge anyway.
  • Route them to the desktop GPU via the existing operator-approval path, rather than attempting them on the VPS.
  • Give model-loading demos their own limits — a separate slice with a much higher MemoryMax, accepting that a 3 GB model needs ~4–6 GB resident.

I did not pick one — it changes what the factory builds, which is yours to decide.

4. Decide whether MemoryMax should be 6G

Deliberately not shipped. Observed demand on the OOM nights was ~6 GiB, which argues for 6G — but that demand was manufactured by the orphan leak that #1587 just fixed. Changing the limit in the same night as the fix would make tonight's result uninterpretable. Let tonight's CGPM output tell us: if a post-fix run still pushes past 3G, raise it; if it settles near 2.2 GiB, 3G is correct. one variable at a time

5. Consider bounding swap rather than zeroing it

MemorySwapMax=0 is the instinctive fix for the thrash, but paired with MemoryMax=3G against ~6 GiB demand it would guarantee an immediate OOM every heavy night — and the swipe, which runs last and is not in a try/finally, would never fire. If the evidence supports bounding swap after tonight, MemoryMax=6G + MemorySwapMax=1G cuts the thrash tail while leaving a valve. wait for data

6. Ignore the Invalid argument cgroup-kill warning

It is cosmetic and not fixable from the unit file. systemd 255's kill path enumerates cgroup.threads after cgroup.procs, and on kernel 6.8 pidfd_open() on a non-leader TID returns EINVAL, which systemd does not whitelist (it whitelists EAGAIN/ESRCH/ENOENT). Measured directly on the box: pidfd_open(1166122) → -22 EINVAL. Cross-checked on mint-desktop with the byte-identical systemd library but kernel 7.0, where the same call returns ENOENT and the warning does not appear. The SIGKILLs were issued before the failing sweep, so nothing was left un-signalled. It disappears on a ≥6.9 kernel.

9. What we could not determine

  • Why two claude processes were still alive on 08-01 at all. All three builds that night ended rc=3, not on a timeout — so the timeout path that orphans grandchildren did not fire. The leak mechanism is proven and fixed, but on 08-01 specifically the leftovers must have come from a different path (a claude sub-agent, or a background stage inside build_demo.py). Tonight's CGPM leftover_procs line will show whether any survive post-fix. This is the one place where the shipped fix may be incomplete, and it is worth saying plainly rather than claiming the case is closed.
  • Why SIGKILL'd PIDs stayed in cgroup.procs for 91 s. A SIGKILLed task cannot be reaped while in uninterruptible sleep; swap-in page faults are the leading explanation given the 07-27 OOM stack, but the process states are gone and this could not be proven post-hoc.
  • What happened to the 2026-07-31 run's terminal journal line. Its wall clock is now known (137m35s, ending ~07:09:45) and its swipe ran (18 rows), so it did reach the end — but its Deactivated/Consumed lines are absent from the journal. Unexplained.
  • Whether the fidelity gate regressed or the builds did. Both are consistent with the data; distinguishing them needs a human look at one rejected demo.
  • Tonight's run (2026-08-02 04:51 UTC) is the real test. It had not fired at the time of writing — it is the first run under #1587, #1588, and #1579's TimeoutStopSec, and the first that will record its own cgroup evidence.
