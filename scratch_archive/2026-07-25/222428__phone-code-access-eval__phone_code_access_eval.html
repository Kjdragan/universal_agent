1. Verdict

The pasted plan's diagnosis is right (two features on one UI; "empty default environment" = you were in cloud sessions; Infisical machine-identity is the correct secrets pattern — it's the same universal-auth flow your repos already use). Full fact-check in Appendix A.

But for the real goal — greenfield projects workable from your phone — the answer is a system, not a per-project fix: one reusable account-level environment created once, a cloud bootstrap baked into /dragan:new-repo so every future repo is born cloud-ready, and a Remote Control server for the one thing cloud sessions can't do (create a new repo). The good news: your scaffold's secret loader already works in the cloud unchanged — verified in its source.

2. The organizing principle: exactly two scopes carry into a cloud session

A cloud session is a fresh Anthropic VM. Everything it has comes from precisely two places — nothing else on any of your machines exists there:

ScopeWhat it carriesWhere you control it
The repo cloneCLAUDE.md, .claude/settings.json hooks, .claude/skills|agents|commands, .mcp.json, all codeCommitted per-repo → so it belongs in the scaffolder, generated once for every new project
The environmentEnv vars + setup script + network allowlistAccount-level at claude.ai/code, and repo-agnostic — verified: repo choice and environment choice are independent steps, the Name field is described as for "multiple environments for different projects or access levels", and /remote-env sets a default (docs scope that command to CLI --cloud starts; first/only environment acts as default generally)

Everything user-level — your global ~/.claude/CLAUDE.md, ~97 user-only skills, dragan plugin marketplaces, settings.local.json, claude mcp add servers — stays home by design. And the VM is not on your tailnet: no scratchpad, no ssh uaonvps, no SSHFS.

Security caveat that follows directly: any secret placed in an environment is visible to every repo and session that uses that environment — and a single cloud session can attach multiple repos at once. So the shared environment must hold only low-blast-radius bootstrap credentials (a least-privilege machine identity), never real project secrets. If you ever have repos of very different sensitivity, give them separate environments.

3. The general design — three layers

Layer 1 — one-time, account level: a single reusable "kevin-standard" environment

Created once in the claude.ai/code web UI; serves every project forever after.

  • Mint a NEW Infisical machine identity for cloud use only — universal-auth, read-only, scoped as tightly as practical. It sits in Anthropic's environment config in plaintext-to-you; keep its blast radius small and revocable independently of the identities your desktop/VPS use.
  • Env vars (the only four lines it ever needs): 
    INFISICAL_CLIENT_ID=<cloud identity id>
INFISICAL_CLIENT_SECRET=<cloud identity secret>
INFISICAL_PROJECT_ID=<project id>
INFISICAL_ENVIRONMENT=production
  • Network: Custom + the "common package managers" checkbox + app.infisical.com + api.z.ai (scaffolded repos run their own inference on GLM) + optionally api.telegram.org — a nice discovery: notify-phone-style pushes CAN work from cloud sessions, because the bot token comes from Infisical, not the tailnet.
  • Setup script: probably none. The estate fetches secrets via plain HTTPS from Python (httpx), so the Infisical CLI + its apt repo are unnecessary. Only if the VM lacks uv: a one-line pip install uv.
  • Optionally /remote-env once in a terminal to pin it as the default for CLI-started cloud sessions.

Layer 2 — per-repo, automatic: extend /dragan:new-repo so every new repo is born cloud-ready

Key verification: the scaffold's lab_common/secrets.py already reads INFISICAL_* from os.environ and its dotenv load is a no-op when .env is absent — so in a cloud VM, Layer 1's env vars flow straight into load_secrets() with zero changes to the loader. Desktop (.env file) and cloud (env config) share one mechanism; no drift.

What the scaffold is missing is the .claude/ layer — it ships none today. Add three small committed assets:

  1. .claude/settings.json — registers a SessionStart hook.
  2. .claude/hooks/session-start.sh — gated on CLAUDE_CODE_REMOTE=true (exact pattern already proven in universal_agent's committed hook): run uv sync to build the venv, then append secrets to $CLAUDE_ENV_FILE so every subsequent Bash command in the session has them. Fail-soft, never blocks a session.
  3. lab_common/cloud_env.py — ~20 lines: call the existing load_secrets(), print KEY=value lines for the fetched secrets (values never logged). The hook pipes this into $CLAUDE_ENV_FILE.

Result: every future /dragan:new-repo project works in a cloud session out of the box — venv built, full secret set loaded, GLM inference routable. The same three files can be dropped into any existing repo to retrofit it (universal_agent only needs the $CLAUDE_ENV_FILE exporter added to its existing hook).

One caveat inherited from the docs: $CLAUDE_ENV_FILE is referenced by the web docs but thinly documented — the first scaffolded repo doubles as the empirical test.

Layer 3 — the creation step: starting a brand-new project FROM the phone

The one thing a cloud session cannot do by default is create a new GitHub repo: its git push is proxy-restricted to the cloned repo's session branch, gh isn't installed, and tokens are proxy placeholders. Kevin's instinct — keep a fully-loaded source repo and stamp copies of it — is right, with one correction:

Use a GitHub template repository, not a fork. GitHub won't fork a repo into the same account that owns it, and a fork carries a permanent parent link you can't cleanly disconnect. A repo flagged as a template does exactly what you want in one step: "Use this template" (web/phone) or gh repo create <name> --template Kjdragan/greenfield_template --private creates a standalone, unlinked, GitHub-backed new repo with fresh history — rename, disconnect, and "brand new project" are all inherent, no automation needed to sever anything.

Primary — phone-only, no computer involved:

  1. Once: build Kjdragan/greenfield_template from the new-repo scaffold assets + the Layer 2 .claude/ cloud bootstrap, flag it as a template. It ships no .env — cloud-native by construction (secrets arrive via the kevin-standard environment).
  2. Per new project, from Chrome on the phone: github.com → greenfield_template → Use this template → type the new name → Create. ~30 seconds, server-side.
  3. claude.ai/code (same browser or the app) → new session on the new repo, kevin-standard environment → the SessionStart hook builds the venv, loads secrets into $CLAUDE_ENV_FILE, and personalizes the placeholder project name to the repo's name (small idempotent first-boot step in the hook).

Alternatives:

  • RC server on the VPS (always-on; needs the one-time claude auth login as ua): connect from the phone and say "/dragan:new-repo for X" — full estate scaffold, richer than the template (VPS deploy, source-env copy). Best when you want the project on the estate machines too, and the fallback whenever the template drifts behind the scaffold.
  • Conversational upgrade (optional, later): put a narrowly-scoped GitHub PAT in Infisical and allowlist api.github.com in the environment — then any cloud session can itself run the template-generate API call, so from the Claude app you'd just say "spin up a new project called X" with no GitHub UI visit at all.

Sync duty: the template repo is a second consumer of the new-repo assets — regenerate it whenever those assets change (small script/CI in dragan-plugins; drift here would silently ship stale scaffolding).

6. Appendix B — universal_agent-specific findings (from rev 1)

  • The repo is already half-wired for cloud: origin/main commits 95 skills, 25 agents, 11 commands, CLAUDE.md, .mcp.json, and a SessionStart hook already gated on CLAUDE_CODE_REMOTE=true that runs uv sync --frozen. The gap is only secrets: .mcp.json needs AGENTMAIL_API_KEY + ZAI_API_KEY, and no committed path loads Infisical without the gitignored .env. Retrofit = Layer 2's exporter added to the existing hook.
  • ZAI MCPs in cloud burn ZAI quota from an Anthropic-side context — prefer built-in WebFetch/WebSearch there, same rule as interactive sessions. Mind the ZAI single-concurrent-session plan if cloud scripts run GLM while VPS agents are active.
  • VPS RC server readiness (checked live): claude v2.1.220 + tmux 3.4 present; login shell has no ANTHROPIC_* vars; user ua has no OAuth creds yet → one-time claude auth login, then claude remote-control in tmux. Phone permission modes for RC exclude Bypass — naturally safer on the prod box.
  • Working-tree-only MCP servers (discord ×2, one with a hardcoded desktop path) aren't at origin/main; don't commit them as-is.
