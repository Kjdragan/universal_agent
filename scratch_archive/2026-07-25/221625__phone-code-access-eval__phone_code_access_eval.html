1. Verdict in three sentences

The core diagnosis is correct and confirmed by the docs: Remote Control and cloud sessions are two different features sharing one UI, "empty default environment" means you were landing in cloud sessions, and Infisical machine-identity is the right secrets pattern for cloud — it is literally the same universal-auth pattern scripts/_claude_launcher.py already uses locally.

But the plan is generic, and your estate changes the answer: the cloud VM is not on your tailnet (no scratchpad, no notify-phone, no ssh uaonvps), the repo already commits 95 skills / 25 agents / .mcp.json / a cloud-gated SessionStart hook, and the one machine that is always on — the VPS — is a better Remote Control host than your desktop.

Recommended order: Remote Control first (desktop now, VPS as the always-on target), cloud sessions second as the fire-and-forget lane — the remaining cloud gap is just two MCP secrets plus a small committed bootstrap hook.

3. What the plan missed (estate-specific)

3.1 The cloud VM is not on your tailnet — a big slice of your workflow can't run there

The sandbox has no Tailscale. From a cloud session there is no scratchpad publishing (uaonvps.taildcc090.ts.net unreachable), no ssh uaonvps, no SSHFS path guarantee, and no notify-phone unless you allowlist api.telegram.org and supply the bot token. Much of the global-CLAUDE.md operating doctrine physically cannot execute in that VM. This is the single biggest reason cloud sessions will always feel like a different, thinner machine than Remote Control.

3.2 Your user-level layer doesn't carry — and mostly shouldn't

The ~30 KB global ~/.claude/CLAUDE.md, ~97 user-level-only skills (hyperframes, dragan plugins, efficient-fable, visual-explainer, …), 10 user commands, and 16 plugin marketplaces stay home. The plan's advice — "commit user config into the repo" — is already done for the parts that matter (see §4), and the rest shouldn't move: most of those skills depend on tailnet, local binaries, or other repos via symlinks, and the global doctrine file contains estate-private operational detail that doesn't belong in more repos than necessary.

3.3 Cloud usage burns your Max rate limits

Confirmed by docs: cloud sessions share rate limits with all other Claude usage on the account; parallel sessions consume proportionally (no separate compute charge). So the "fire lots of parallel cloud tasks" pattern competes directly with your interactive Fable/Opus budget. The estate doctrine (bulk background → ZAI/GLM on the VPS) still stands; cloud sessions are a convenience lane, not a bulk lane.

3.4 Odds and ends that will bite

  • ZAI MCPs in cloud sessions burn ZAI quota from an Anthropic-side context — the committed .mcp.json ships web-reader / web-search-prime. In cloud, prefer built-in WebFetch/WebSearch (same rule as interactive sessions today).
  • gh is not preinstalled in the VM; git push is proxy-mediated and restricted to the session's branch. PR flow still works (auto-merge lives GitHub-side), but scripts that shell out to gh won't.
  • Teleport exists and is useful glue: claude --teleport / /tp pulls a cloud session + its branch down to the desktop to finish with the full estate. Cloud-from-phone → teleport-at-desk is a legitimate workflow.
  • Keep cloud sessions Private. On Max, visibility is Private/Public — Public means any signed-in claude.ai user.
  • Mobile app limits: can start cloud sessions, steer/answer/interrupt, and join Remote Control sessions (QR or list). No /plugin//resume; no Bypass permission mode from the phone (cloud: Accept edits/Plan/Auto; RC: Manual/Accept edits/Plan).
  • The two uncommitted working-tree MCP servers (discord, discord-intelligence-bridge with a hardcoded /home/kjdragan/... path) aren't at origin/main; if ever committed as-is, the absolute path breaks everywhere but the desktop.

5. Recommendation — three tiers

Tier 1 — Today, zero setup: Remote Control on the desktop

Your claudereal wrapper already strips ANTHROPIC_*, so desktop sessions are fully RC-compatible right now. Either flip /config → "Enable Remote Control for all sessions", or run claude remote-control (server mode) in tmux so the phone can start new sessions against the desktop, not just join existing ones. Full estate: Infisical secrets, tailnet, scratchpad, all 100+ user skills, GPU.

Limits: desktop must be awake; anything launched via zai (GLM base URL) can never RC.

Tier 2 — The always-on answer: Remote Control server on the VPS

This is the option the plan couldn't know about. Verified today: the VPS has claude v2.1.220 and tmux 3.4, no ANTHROPIC_* vars in the login shell, but user ua has no OAuth credentials yet. One-time setup: claude auth login as ua, then keep claude remote-control alive in tmux. Your phone then always has a green session to connect to — against the production box, with /opt/universal_agent/.env present so the full secret bootstrap works, tailnet-native (scratchpad and notify-phone work from inside the session), and independent of whether the desktop is on.

Decide which account's Max limits it spends (it must be OAuth — the ZAI plan can't drive RC). Phone permission modes for RC exclude Bypass, so it's naturally safer on a prod box.

Tier 3 — Fire-and-forget lane: finish cloud enablement (small PR + one-time console work)

Adopt the plan's Infisical architecture with three corrections:

  1. Mint a NEW machine identity for cloud only — least-privilege, read-only, scoped to the handful of secrets a sandbox should ever see (not the full production set, and not the identity the desktop/VPS use). It sits in Anthropic's env config in plaintext-to-you; keep its blast radius small and revoke it independently.
  2. You probably don't need the Infisical CLI or its apt repo at all. The estate already authenticates headless via universal-auth REST calls with httpx (_claude_launcher.py pattern) — and the SessionStart hook runs after uv sync, so httpx is available. A ~30-line committed script, gated on CLAUDE_CODE_REMOTE=true, fetches secrets and appends exports to $CLAUDE_ENV_FILE. Fewer moving parts, one less network domain, no root installs.
  3. Test the undocumented bit before trusting it: whether env-config vars reach .mcp.json ${VAR} expansion. If yes, put AGENTMAIL_API_KEY/ZAI_API_KEY directly in the env config and MCP works. If no, MCP servers stay dead in cloud (hook-written env likely lands after MCP spawn) — acceptable, since built-in tools cover web needs there.

Network access: Custom + the package-manager defaults + app.infisical.com (drop artifacts-cli.infisical.com if you skip the CLI). Keep sessions Private.
